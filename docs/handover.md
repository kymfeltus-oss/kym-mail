# Engineering handover

KYM Mail contains the Gate 1 foundation through Gate 5 Job Search, the Gate 6/6A authoritative Master Career Profile, and Gate 6B Career Match, alongside previously implemented isolated later modules. It is a Next.js/React/TypeScript application with real Supabase authentication and RLS, unified mail, contextual Projects, deterministic scheduling, vendor-neutral job discovery, normalized Saved Jobs, structured source-backed career facts with field provenance, persisted evidence-linked job analyses, and validated versioned resume exports.

Gate 6A is the source-intake and owner-review foundation for the Master Career Profile. It reuses the two already reviewed resume extraction records by SHA-256, persists candidates, performs deterministic comparison, auto-confirms only safe exact dual-source facts, and exposes one Review Needed queue for exceptions. Owner review/edit paths create immutable numbered fact versions and provenance; controlled imports cannot silently replace an owner-confirmed fact. No new AI provider or secret is required, and raw resumes must remain outside the repository and deployment.

## Ownership and service relationships

The canonical source repository is `https://github.com/kymfeltus-oss/kym-mail`, and this project directory is its root. KYM Mail is intentionally isolated from the unrelated parent `Identification-Engine` repository and its history. Production is `https://www.kymmailapp.com` in the Vercel project `kym-mail`. Persistence and owner authentication use Supabase project `wrmemvvzdxxzwstnjcau`. Gmail OAuth, Gmail API, and Pub/Sub resources use Google Cloud project `kym-mail`.

Vercel and local development receive secrets only through environment stores. Do not put secret values, `.env` files, downloaded OAuth credential JSON, screenshots containing credentials, Supabase service-role keys, OAuth state secrets, or token-encryption keys in Git, documentation, support output, or application logs. Rotate any credential immediately if it is displayed or shared outside its intended secret store.

Major directories: `src/app` owns routes and server actions; `src/components` owns shared presentation; `src/domain` owns vendor-neutral contracts; `src/lib` owns auth, Supabase access, environment handling, errors, and logging; `supabase/migrations` owns schema history; `docs` explains operations and architectural law.

Follow the README to run, test, and build. Deployment is standard Vercel plus independently managed Supabase migrations. Runtime dependencies are Next.js, React, Supabase SSR/client, Zod, Lucide icons, `docx`, and `pdf-lib`. Tailwind and quality tooling are development dependencies.

KYM Mail records multiple owner mail identities. `kym@kymmailapp.com` is the default professional/direct sender and `info@kymmailapp.com` is the general/business sender. They use the owner-controlled production domain because `kym.com` was unavailable. They are identities within one unified mailbox experience, not separate apps or authentication users. This mail-identity change does not by itself change the private owner's Supabase authentication email.

Gate 3 uses one Project table with five validated types and four persisted statuses. Project type is intentionally immutable in V1. Parameters are explicit versioned Zod contracts persisted as JSONB; they are not a generic extension bucket. The owner-facing delete policy is Archive/Restore. The default sender references a real mail identity; if it becomes unavailable, the Project remains readable and Compose requires an explicit usable sender instead of silently falling back. Ordinary global mail remains available with no Project.

Gate 4 uses one relational scheduled-message snapshot, private Supabase Storage attachments, an explicit five-state machine, service-role-only atomic claim/recovery functions, and a protected one-minute Vercel Cron executor. It sends through the existing Google provider, preserves the selected identity and Project, synchronizes successful messages into ordinary Sent/threads, and prevents double sends with conditional state transitions plus a deterministic RFC Message-ID. Edit/reschedule/cancel operate only before claim; cancellation is retained and idempotent. See `docs/deployment.md` for recovery and cron operations.

Gate 5 uses the Adzuna standard Job Search API behind `JobSearchProvider`. Search is global, deterministic, and never AI-generated. Job Search Project parameters can pre-populate supported controls but remain editable. Search results are normalized, safely rendered, deduplicated, and source-attributed; they are not persisted until Save. The server re-verifies the provider result before creating/updating one authoritative `job_opportunities` row. A saved opportunity may associate with multiple active Job Search Projects without duplication. The only lifecycle states are Saved and Archived. Provider descriptions are snippets; original postings remain authoritative.

Gate 6 uses migrations `202608240010_master_career_profile.sql`, `202608250015_career_owner_editing.sql`, and `202608250016_fix_profile_history_target.sql` plus the generic `career:import` administrative command. It retains canonical organizations, titles, experiences, clients, education, credential status, categorized skills, projects, accomplishments, quantified metrics, aliases, field provenance, and immutable owner-change history. The approved profile contains eleven employment records, including three explicitly partial earlier-employer records with no inferred dates/titles, and one canonical ASC606 Revenue Engine project with the ASC 606 Audit Automation alias. The authenticated owner may edit allowlisted factual fields; RLS requires resolved owner authority and triggers preserve before/after snapshots. Service-role ingestion remains isolated and authority guarded. The original PDFs and temporary intake file are deliberately not committed.

Gate 6B reuses migrations `202608240011_job_intelligence.sql` and `202608240012_job_intelligence_partial_gaps.sql`, then closes the current contract with `202608250020_gate6b_career_match_contract.sql`. Saved-job analysis extracts grounded structured requirements, independently distinguishes required/preferred/responsibility/context importance, matches only confirmed authoritative Gate 6 evidence, calculates deterministic `weighted-requirement-v2`, persists requirement/evidence/WHY results, and never reads unresolved Gate 6A candidate facts. Re-analysis is explicit; refresh does not rerun an unchanged description. A failed attempt leaves the prior success recoverable, while a changed analyzer contract marks it stale.

The previously implemented tailored-resume module uses migration `202608250013_tailored_resume_engine.sql`. Its persisted deterministic plan may consume positive/partial Career Match evidence while the Gate 6 profile remains the only factual authority. It is outside Gate 6B and was not invoked or changed by this implementation.

Gate 9 implements the owner-secured contact-intelligence foundation in migration `202608250014_contact_intelligence.sql`: organization/search/contact/email/provenance persistence, deterministic target-role selection and ranking, conflict/freshness rules, exact email states, manual entry, preferred selection, cooldowns, and a responsive production UI. The Apollo organization/people/business-email adapter is implemented and activated only by server-only `APOLLO_API_KEY`; no key is currently configured locally or in Vercel, and no independent verification provider is configured. Therefore production still renders the truthful unavailable state and Gate 9 remains PARTIAL until Apollo is configured and the real CFO-job journey is live-verified.

Intentionally deferred after Gate 9: cover-letter generation, outreach email generation, automatic sending/follow-up, automatic applications, reply classification, interview coaching, additional mail/job providers, saved-search monitoring, and a general LLM provider. The locked future career-outreach architecture is maintained in `docs/future-career-outreach-workflow.md`.
