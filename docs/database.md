# Database

Supabase-managed PostgreSQL is the database. Migrations in `supabase/migrations` are the only schema change mechanism and run in filename order.

Gate 1 established `public.profiles` and owner-scoped `public.mail_accounts`. Gate 2 adds `mail_connections`, the server-only `mail_connection_credentials`, unified `mail_threads`, `mail_messages`, attachment metadata, and deduplicated provider notifications. A connection is distinct from a sending identity: both configured addresses link to the same Google mailbox connection. Provider IDs are unique within that connection, and each thread/message retains the relevant account identity.

Migration `202608240007_projects.sql` is the authoritative Gate 3 schema. It adds one `projects` table, `project_activity`, and nullable `project_id` foreign keys on existing threads/messages. Project types are `JOB_SEARCH`, `BUSINESS_OUTREACH`, `PARTNERSHIP`, `NETWORKING`, and `CUSTOM`; statuses are `ACTIVE`, `PAUSED`, `COMPLETED`, and `ARCHIVED`. The default identity is a relational foreign key to `mail_accounts` with `ON DELETE SET NULL`, so an unavailable or removed identity never invalidates the Project or causes silent sender substitution.

Type-specific parameters are versioned JSONB objects (`parameter_schema_version = 1`) whose explicit per-type Zod schemas are authoritative at the server boundary. The database constrains the container shape and owner relationships; JSONB does not hold normalized mail, contact, job, resume, or identity records. Owner-consistency triggers prevent cross-owner Project/account/thread/message associations. RLS restricts Projects to the authenticated owner and exposes Project Activity as owner-readable but trigger-written. Anonymous access has no policy. Archive is the normal deletion policy; there is no owner-facing permanent-delete route.

Migration `202608240008_scheduled_mail.sql` is the authoritative Gate 4 schema. `scheduled_messages` stores typed delivery state and the exact approved mail snapshot; `scheduled_message_attachments` stores private object metadata and SHA-256 integrity values; `scheduled_message_events` stores deterministic schedule activity. Status is the `scheduled_mail_status` enum: `SCHEDULED`, `PROCESSING`, `SENT`, `FAILED`, or `CANCELLED`. Database checks require valid cardinalities, state-dependent claim/provider fields, and owner-consistent account/Project/attachment relationships.

`claim_due_scheduled_messages()` performs the only delivery claim transition with a row lock and `SKIP LOCKED`, so overlapping invocations cannot claim the same row. `recover_stale_scheduled_messages()` releases abandoned claims after ten minutes or fails them at the attempt limit. Both functions are revoked from public, anonymous, and authenticated roles and executable only by `service_role`. Owner RLS is read-only at the tables; mutations flow through authenticated, same-origin server routes that re-resolve the owner and conditionally update status/version. The private Storage bucket has no client policies and a 10 MB per-object limit.

Migration `202608240009_job_search.sql` is the Gate 5 schema. `job_opportunities` persists only validated normalized fields and narrow reconciliation/provenance metadata; it does not store the raw Adzuna response. The unique owner/provider/provider-job key makes repeated Save idempotent, while a unique owner/source-URL index catches provider duplicates with changing identifiers. Status is deliberately limited to `SAVED` and `ARCHIVED`.

`job_opportunity_projects` is the normalized many-to-many relationship between one authoritative opportunity and active Job Search Projects. A database trigger verifies that the opportunity and Project share an owner, that the Project is `JOB_SEARCH`, and that it is not archived. `job_project_activity` records association/removal events for the Project workspace. All three tables use owner-only RLS; anonymous access has no policy. Source/application URLs must be HTTPS, descriptions are bounded plain text, salary ranges are internally consistent, and employment/work-arrangement values are constrained.

Migration `202608240010_master_career_profile.sql` is the Gate 6 schema. It adds typed authority/source/category enums and normalized tables for sources, profile, organizations, titles, experiences, education, credentials, skills, projects, accomplishments, metrics, skill relationships, aliases, and provenance. Unique owner/canonical keys prevent duplicate employment, project, title, organization, skill, accomplishment, and metric records. Date, current-role, metric-value, parent, and completeness checks reject invalid or invented structure; relationship triggers reject cross-owner and orphan references.

Career tables apply owner-only RLS and have no anonymous policy. Migrations `202608250015_career_owner_editing.sql` and `202608250016_fix_profile_history_target.sql` add column-restricted owner updates, require every authenticated edit to retain the same owner and become `RESOLVED`, and capture every changed field plus complete before/after snapshots in the private, append-only `career_fact_history` table. Owners can read history but cannot insert, change, or delete it directly. Controlled service-role imports remain Zod-validated, canonically resolved, idempotent, and authority guarded; their database changes are separately attributed as controlled imports. Source PDFs and temporary intake manifests are not stored in the application, database, repository, or public assets; their hashes and field-level provenance provide traceability without copying source documents.

Migrations `202608240011_job_intelligence.sql` and `202608240012_job_intelligence_partial_gaps.sql` form the Gate 7 schema. `job_analyses` stores analysis state, fingerprints, score, and summaries; `job_analysis_requirements` stores original wording, normalized concept, category, importance, match state, and material-gap flags; `job_analysis_evidence` stores owner-validated career-record relationships. The corrective migration permits an optional structured gap reason on `PARTIAL_MATCH` while continuing to require one for `NO_MATCH` and `UNVERIFIED`. Only one `ANALYZING` row and one `COMPLETE` row may exist per job. A completed analysis requires structured requirements, and every positive/partial match requires persisted evidence that `career_entity_belongs_to_owner` accepts. Description and career-table triggers mark `COMPLETE` analyses `STALE`. Owner-only RLS applies; anonymous roles have no policy.

Migration `202608250013_tailored_resume_engine.sql` is the Gate 8 schema. `tailored_resumes` provides one owner/job aggregate and points to its last successful current version. `tailored_resume_versions` stores immutable version snapshots, deterministic plans, provider/mode, validation results, analysis and career fingerprints, generation lineage, and explicit `DRAFT`, `GENERATING`, `READY`, `FAILED`, `STALE`, and `ARCHIVED` states. `tailored_resume_evidence` links every generated or selected content key to a Gate 6 career entity, and its security-definer trigger accepts only same-owner authoritative records. `tailored_resume_exports` audits format, safe filename, and SHA-256 without persisting public binaries.

Owner-consistency triggers reject cross-user jobs, analyses, parents, versions, evidence, and exports. A failed regeneration never changes `current_version_id`. Job-description, analysis, and Gate 6 career changes mark successful versions stale without deleting them. Authenticated owners receive only RLS-scoped table privileges; anonymous users have none. Export routes re-resolve both resume and version ownership before generating a private, no-store response.

Migration `202608250014_contact_intelligence.sql` is the Gate 9 schema. `job_contact_organizations` stores the job-scoped canonical organization without silently guessing a domain. `job_contact_searches` stores the explicit search state, version, targeted roles, provider identities, cost/cooldown metadata, and safe failure. `job_contacts` stores normalized professional identity, job-specific classifications and deterministic ranking; one active preferred contact is allowed per owner/job. `job_contact_sources` preserves field-level provenance and conflicting claims. `job_contact_emails` separates discovery from verification and prevents pattern-based candidates from becoming `VERIFIED` or `DELIVERABLE`. Owner-consistency triggers, stale-on-company-change behavior, and RLS cover every table.
