# Architecture

## KYM Mail is Logic-Driven and AI-Executed

Deterministic application logic owns state, validation, workflow progression, permissions, persistence, scheduling, provider orchestration, factual records, approval boundaries, business rules, and error handling. Future AI may execute bounded extraction, interpretation, ranking, summarization, personalization, drafting, and classification tasks. It is never the state machine or source of truth.

The required future flow is: input contract → deterministic validation → AI execution → structured response → schema validation → provenance validation → business-rule validation → persisted derived result. A `prompt → response → UI` design is prohibited.

Data has three conceptual layers. **Authoritative data** contains human-controlled facts and operational records and cannot be directly modified by AI. **Derived intelligence** contains validated AI-assisted interpretations and must retain provenance to supporting authoritative records. **Presentation** contains regenerable copy or views and never becomes the factual source of truth. Gates 1–6A persist authoritative owner, mail, Project, scheduling, source-backed JobOpportunity, and Master Career Profile records. Gate 6B persists derived job-match intelligence that must resolve every positive match to confirmed Gate 6 career records.

## Master Career Profile

Gate 6 adds a normalized owner-scoped career data layer rather than a resume document or biography blob. Profile identity, organizations, canonical titles, employment/engagement records, clients, education, credentials, skills, projects, accomplishments, and metrics are separately queryable. Generic aliases preserve alternate employer, title, technology, skill, and project wording without fuzzy replacement of authoritative facts. Field-level provenance identifies the reviewed source, page/locator, source wording, source role, and any explicit resolution.

Gate 6A wraps the existing normalized records in a minimal fact lifecycle. `career_source_extractions` caches exactly one successful reviewed extraction per source hash and schema version. `career_candidate_facts` retains normalized source claims and deterministic `SUPPORTED_BY_BOTH`, single-source, or conflict classification. `career_facts`, `career_fact_sources`, and `career_fact_versions` hold the current authoritative value, provenance, confirmation method, and immutable numbered history. Exact low-risk skill/system agreements may use `AUTO_CONFIRMED_SOURCE_AGREEMENT`; dates, titles, metrics, credentials, education, accomplishments, ambiguous language, and unique source claims never do. Owner confirmation is an overwrite boundary: imports can create review suggestions but cannot update an owner-confirmed normalized field or fact.

`career_fact_dependencies` is deliberately small. A changed fact marks linked `DRAFT` or `UNSENT` job-match, resume-version, or outreach-draft work stale. `SENT` and `PUBLISHED` records remain immutable historical snapshots. Gate 6A creates only this foundation; it adds no job matching, resume generation, hiring intelligence, email intelligence, or outreach behavior.

KF Resume controls chronology and exact titles. The secondary resume can add non-conflicting context and metrics but cannot downgrade authoritative or resolved records. Owner confirmations resolve the B.S. in Accounting at UNT, Aston Carter/ESI relationship, one canonical ASC606 Revenue Engine project with the ASC 606 Audit Automation alias, and current CPA Candidate status. Controlled ingestion is a server-only administrative boundary. The product exposes owner-only review and entity-specific factual edits: every authenticated edit is Zod-allowlisted, constrained by column grants and RLS, promoted to `RESOLVED`, and recorded as an immutable before/after history entry. Career edits mark dependent job analyses and resume versions stale through deterministic database triggers. AI/provider boundaries have no career mutation authority.

## Job intelligence

Gate 6B compares a saved job description with the authoritative Master Career Profile. Deterministic logic owns the independent `REQUIRED`, `PREFERRED`, `RESPONSIBILITY`, and `CONTEXT` classification, match state, weighted scoring, evidence resolution, stale detection, re-analysis, persistence, and authorization. A bounded interpreter may extract strict structured requirements and rank candidate evidence; it cannot invent career facts, assign the final percentage, or mutate Gate 6 records. Source-text grounding rejects invented requirements. Every positive or partial match stores relationships to real `AUTHORITATIVE` or owner-`RESOLVED` career record IDs; `SUPPLEMENTAL` records and unresolved Gate 6A candidate facts are ineligible. The WHY screen is derived from the same persisted requirement/evidence result and does not generate a résumé, cover letter, or outreach.

Next.js route/server boundaries own transport and rendering. Domain code owns business concepts and provider contracts. Supabase owns managed PostgreSQL and authentication. UI components do not query the database directly. Future providers implement the small domain interfaces and are injected into domain services. State transitions remain deterministic and persisted before presentation.

## Unified mailbox identity direction

One authenticated owner may have multiple `mail_accounts` in a single KYM Mail workspace. Future inbox, sent, draft, scheduled, message, and thread models must retain their provider/account identity while remaining unified views—not duplicated mailbox implementations. Compose must offer a From selector whenever multiple active identities exist. Professional/direct outreach defaults to `kym@kymmailapp.com`; general or administrative communication defaults to `info@kymmailapp.com`. A future project may reference a default identity. The addresses use the owner-controlled production domain because the originally proposed `kym.com` domain was unavailable. Gate 1 established identity ownership and defaults; Gate 2 verifies their real provider configuration before enabling mail behavior.

## Projects as shared-service context

Gate 3 implements one owner-scoped `projects` model as an optional contextual layer over the existing global application. Project types are deterministic and immutable after creation. Type-specific parameters use explicit version-1 Zod schemas and server validation before JSONB persistence. Projects reference a real `mail_accounts` row for their default sender, while Compose remains the single shared engine and supports `Project: None` for ordinary mail.

Threads and messages have nullable application-owned Project associations. A linked thread is the authoritative continuity mechanism: later messages and incoming replies inherit the existing thread's Project without changing provider identifiers or duplicating mail. A small deterministic activity log records only persisted creation, update, status, send, and reply events. Archive is the owner-facing deletion policy; permanent deletion is intentionally absent.

Gate 5 implements the first step of the locked Job Search → Career Match → Decision Maker → Email Intelligence → Individualized Outreach roadmap in [future-career-outreach-workflow.md](future-career-outreach-workflow.md). Gate 6B is the current Career Match contract. Previously implemented later modules remain isolated from this Gate 6B change; no Gate 7 workflow is started here. Shared services consume validated Project context; they do not create Project-specific copies of Mail, Compose, Job Search, Contacts, Email Discovery, Resume Studio, or AI systems.

## Real job discovery

Gate 5 adds a vendor-neutral `JobSearchProvider` and one Adzuna adapter. A deterministic service validates the owner query, preserves the original text, normalizes quoted phrases/terms, maps only supported filters, calls the provider server-side, validates each response record, strips provider HTML to plain text, deduplicates by provider identity/source URL/conservative fingerprint, and calculates explainable matched-term indicators. Provider payloads never become the application domain model, and raw response blobs are not persisted.

Search results remain ephemeral until the owner saves one. Saving re-runs the provider request and resolves the provider job ID on the server, preventing a client-authored listing from becoming authoritative. One `job_opportunities` record is unique per owner/provider/provider-job ID and may associate with multiple active `JOB_SEARCH` Projects through `job_opportunity_projects`. Saved/Archived is the complete Gate 5 lifecycle. Search is global; a Project only supplies editable initial controls and persisted association context.

## Gate 8 Hiring Intelligence

Gate 8 reuses the vendor-neutral `PeopleDiscoveryProvider` boundary. Deterministic application logic classifies each posting as `DIRECT_EMPLOYER`, `AGENCY_RECRUITER`, or `UNKNOWN`, selects a context-specific role strategy, validates provider records, rejects wrong-organization people, assigns independent verification and role-relevance states, ranks an explainable shortlist of at most five, and persists field-level provenance. Direct-employer searches prioritize the functional hierarchy; agency searches prioritize the poster, recruiter, search consultant, or practice lead without inferring a confidential client. CFO strategy does not recommend an incumbent CFO by default, and private-equity contacts require explicit sponsor evidence. No result is called a hiring manager without reliable evidence.

Research is explicit, cached by job/company/context fingerprint, and refreshed only after owner action. A page refresh is read-only. One person becomes the approved contact only through the owner-only approval RPC; rejection leaves alternatives available. Manual people remain `UNVERIFIED`. Gate 8 neither invokes the dormant email interfaces nor persists new email intelligence.

## Scheduled delivery

Gate 4 extends the existing Compose and Mail Core instead of creating a second mail system. A `scheduled_messages` row is the authoritative approved delivery snapshot: sender identity, recipients, content, provider thread/reply context, Project, canonical UTC instant, display timezone, status, attempts, and provider result. Attachments are relational metadata backed by the private `scheduled-mail-attachments` Supabase Storage bucket. The snapshot remains editable only while `SCHEDULED`; optimistic versions and conditional updates reject stale edits and mutations.

The deterministic state machine is `SCHEDULED → PROCESSING → SENT`, `SCHEDULED → CANCELLED`, or `PROCESSING → SCHEDULED/FAILED`. A Vercel Cron request invokes one protected executor every minute. PostgreSQL claims eligible rows atomically with `FOR UPDATE SKIP LOCKED`; the executor revalidates the exact sender, retrieves and checksums attachments, then calls the existing `MailProvider`. A stable RFC Message-ID lets retries search Gmail before sending, preventing another send after an ambiguous provider response. Successful delivery is synchronized into the ordinary Sent/thread model with the preserved Project. The executor boundary is replaceable without changing Compose or the provider contract.

## Gate 7 Interactive Resume Studio

The Master Career Profile remains factual authority; the Master Resume is a versioned, owner-approved presentation layer. A job-specific version references an approved Master Resume version, one current Career Match analysis, the JobOpportunity, and the originating Job Search Project when present. Deterministic planning consumes persisted requirements, evidence, WHY, underselling, and strategy findings before any provider boundary. Refresh performs reads only, while an input fingerprint reuses an existing successful generation for unchanged dependencies.

Every substantive block carries Career Fact references. The validator re-resolves identity, employment, dates, education, credentials, skills, projects, metrics, unsupported requirements, and lexical grounding before a version enters REVIEW or APPROVED. Material diffs are computed against the Master Resume and store individual owner decisions. Approved content is an immutable snapshot; later Career Profile or Career Match changes mark it STALE without rewriting it.

Recipient HTML uses a stripped public view with no evidence identifiers or internal analysis. New links require an APPROVED version, use 256-bit random tokens, and store only SHA-256 hashes; revocation is checked server-side on every request. Executive and ATS PDFs are generated from the same approved content with selectable text. Gate 8 Hiring Intelligence is not part of this workflow and may later consume only an explicit approved resume snapshot identifier.

## Calendar and paid consultations

Calendar is an additive bounded context. Cal.com owns availability and Google Calendar event creation; KYM Mail owns only consultation configuration, manual payment-proof review, secure release, and booking-state reconciliation. Cash App has no API or credential boundary in this repository. The deterministic lifecycle is `AWAITING_PAYMENT → PAYMENT_SUBMITTED → PAYMENT_APPROVED → BOOKING_RELEASED → BOOKED`, with explicit `PAYMENT_REJECTED` and `CANCELLED` exits. Application services and a database RPC own transitions; AI has no role.

Public intake writes through a server-only Supabase client after strict contact, MIME, extension, size, and magic-byte validation. Proof bytes live in the private `consultation-payment-proofs` bucket while owner-scoped relational metadata and SHA-256 live in PostgreSQL. The browser never receives a proof object path or storage credential. Owner review uses existing authentication and Mail Core. Approved access uses 256-bit random tokens with only SHA-256 persisted, a 30-day expiry, provider prefill, and an exact request ID in Cal.com metadata. Signed, deduplicated webhooks make `BOOKED`, rescheduled, and `CANCELLED` state persistent.
